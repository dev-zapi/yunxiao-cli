# PR Documentation Skill

## 调用时执行

当此技能被调用时，先判断用户意图和已有上下文：

- **创建/更新模式**：需要代码变更信息，执行下方的 git 收集步骤。
- **评审模式**：如果用户已提供 PR 文档内容，跳过 git 收集，直接进入评审流程；如果用户仅要求评审但未提供文档，则仍需执行 git 收集以获取 diff 用于校验文档准确性（对照文档描述与实际代码是否一致）。
- **非 git 仓库**：如果当前目录不在 git 仓库中，跳过 git 收集步骤，直接从用户提供的上下文开始。

git 收集步骤：

1. 确定 base branch：优先用 `git rev-parse --abbrev-ref origin/HEAD | sed 's|origin/||'`（快速），失败时回退到 `git remote show origin | grep HEAD`。如果两者均失败，默认使用 `main`。
2. 并行运行下面两个命令获取变更概览：
   - `git log <base>..HEAD --oneline`
   - `git diff <base>..HEAD --stat`
3. 如果变更涉及接口/数据/任务，补充 `git diff <base>..HEAD` 获取完整 diff。
4. 检查 `.github/PULL_REQUEST_TEMPLATE.md` 是否存在，如有则优先遵循其结构。
5. 如果用户提供了额外上下文（需求文档、Issue 链接、测试输出等），一并纳入。

之后按用户意图进入创建、更新或评审流程。如果用户未指定，默认进入创建流程。

## 用途

用于创建、更新和评审 PR 文档，确保评审人员能快速理解变更背景、改动范围、验证结果、影响风险和重点评审位置。

适用场景：

- 根据代码 diff、提交记录、需求文档或实现说明创建 PR 文档。
- 根据新增变更更新已有 PR 文档。
- 评审 PR 文档是否清晰、完整、可验证。
- 创建仓库级 PR 模板。
- 将零散说明整理为符合社区实践的 PR 描述。

## 核心原则

PR 文档必须回答：

| 问题 | 说明 |
| --- | --- |
| What | 本次 PR 做了什么，新增、修复、调整了哪些能力 |
| Why | 为什么需要这些变更，关联什么需求、Issue、缺陷或背景 |
| How tested | 实际执行了哪些自动化或手工验证，结果是什么 |
| Impact | 影响哪些接口、任务、数据、配置、页面、兼容性或部署流程 |
| Review focus | 希望评审人员重点关注哪些风险点或实现细节 |

文档应面向 reviewer，而不是只复述提交记录。优先说明业务能力变化、兼容性和风险，而不是机械列文件。

## 标题规范

推荐使用 Conventional Commits 风格：

```text
<type>[optional scope]: <description>
```

常用类型：

| 类型 | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档变更 |
| `refactor` | 不改变行为的重构 |
| `perf` | 性能优化 |
| `test` | 测试变更 |
| `chore` | 构建、依赖、配置等维护变更 |

示例：

```text
feat(decision-tree): support enhanced product source fields
fix(sync-task): prevent duplicate cleanup records
docs(pr): clarify review checklist
```

破坏性变更必须在标题或正文中显式标记：

```text
feat(api)!: change product source response schema
```

或：

```text
BREAKING CHANGE: product source response no longer returns legacy field `xxx`.
```

## 标题生成

从提交历史推导 PR 标题：

1. 检查 `git log` 输出：如果最近 3 条提交中超过一半符合 `<type>[scope]: <description>` 格式，直接提取最核心的一个作为 PR 标题。
2. 若不满足上述条件（提交信息杂乱或不符合规范），按以下规则重新推导 type：
   - 新接口/新页面/新能力 → `feat`
   - bug 修复 → `fix`
   - 仅文档 → `docs`
   - 不改变行为的代码调整 → `refactor`
   - 性能优化 → `perf`
   - 仅测试 → `test`
   - 构建/依赖/配置 → `chore`
3. scope 从变更文件路径推导，如 `src/decision-tree/` → `(decision-tree)`；跨模块可不写 scope。
4. description 用一句话概括核心业务变化，不超过 50 字。面向 reviewer 描述能力变化而非机械复述提交。

## 模板选择

根据变更复杂度选用模板：

- **精简模板**（见下文）：纯文档、小修复、低风险变更。5 个核心章节 + 最简 Checklist。
- **标准结构**（即完整模板）：功能、接口、数据、任务、配置或跨模块变更。8 个章节 + 完整 Checklist + 可选项目增强表格。

默认使用标准结构，仅在明确属于低风险小变更时使用精简模板。

## 标准结构

创建或更新 PR 文档时，默认使用以下结构：

```markdown
## 背景

<说明为什么需要改，关联需求、Issue、缺陷、原型或上下游背景。>

## 变更内容

<说明本 PR 做了什么，按功能、接口、任务、数据或模块分组。>

## 影响范围

<说明影响哪些接口、任务、数据库、配置、页面、权限、部署或历史数据。>

## 测试说明

<只写真实执行过的测试、验证命令和结果；未执行需说明原因。>

## 截图/示例

<UI、接口响应、任务日志或 before/after 示例；不适用可写“无”。>

## 兼容性与风险

<说明是否有破坏性变更、性能风险、数据风险、安全风险和处理方式。>

## Review 重点

<告诉 reviewer 最需要关注哪些文件、逻辑、边界条件或风险点。>

## Checklist

- [ ] 已完成自测
- [ ] 已补充或更新测试
- [ ] 已更新相关文档
- [ ] 已确认无敏感信息
- [ ] 已说明兼容性和风险
- [ ] 无破坏性变更，或已明确标记并说明迁移方式
```

## 项目增强结构

如果 PR 涉及接口、异步任务、数据库、SQL 或配置，必须补充结构化说明。

### 接口变更

```markdown
| 接口 | 请求变更 | 响应变更 | 兼容性 |
| --- | --- | --- | --- |
| `POST /api/example` | 新增 `xxx` | 返回 `yyy` | 兼容旧请求 |
```

### 任务变更

```markdown
| 任务 | 触发方式 | 执行步骤 | 观测方式 |
| --- | --- | --- | --- |
| `example-sync` | 接口触发/定时触发 | step1, step2 | 任务状态、步骤日志 |
```

### 数据变更

```markdown
| 表/字段 | 变更 | 用途 | 兼容性 |
| --- | --- | --- | --- |
| `example_table.xxx` | 新增字段 | 存储业务状态 | 可为空/有默认值 |
```

### 重点修改位置

```markdown
| 文件 | 重点 |
| --- | --- |
| `ExampleController.java` | 接口入口和权限校验 |
| `ExampleService.java` | 核心业务编排 |
| `ExampleMapper.xml` | 查询条件和写入逻辑 |
| `ExampleTest.java` | 关键场景覆盖 |
```

## 创建 PR 文档流程

1. 先收集上下文（如"调用时执行"步骤尚未完成，先执行之）：
   - 从 `git log <base>..HEAD --oneline` 提取提交历史，识别每个提交的类型和范围。
   - 从 `git diff <base>..HEAD` 获取完整代码变更。
   - 读取用户提供的需求文档、Issue 链接、测试输出。
   - 检查 `.github/PULL_REQUEST_TEMPLATE.md`，如存在则基于其结构组织内容。
2. 按"模板选择"规则，根据变更范围决定使用精简模板还是标准结构。
3. 识别变更类型：功能、修复、文档、重构、测试、配置、数据库、接口、异步任务。
4. 提炼背景和目标：说明为什么改，以及改完后支持什么能力。
5. 分组描述变更：按业务能力、接口、任务、数据或模块分组，不按提交顺序机械罗列。
6. 写明影响和兼容性：包括旧数据、旧接口、旧页面、默认行为、权限、安全、性能、部署、回滚。
7. 写明真实测试：只记录实际执行过的命令、场景和结果；未执行必须说明原因。
8. 给出 Review 重点：指出高风险文件、核心逻辑、边界条件和希望 reviewer 判断的内容。
9. 最后检查 Checklist：确保无空泛描述、无未填占位符、无虚假测试、无敏感信息。

## 更新 PR 文档流程

更新已有 PR 文档时：

1. 保留原有有效内容，不重写成完全不同风格，除非原文结构严重缺失（定义：缺少 3 个及以上核心章节 —— 背景、变更内容、影响范围、测试说明、兼容性与风险、Review 重点、Checklist 中的任意 3 个。此时应保留已有内容，补充缺失章节）。
2. 根据最新 diff 或用户说明补充新增变更。
3. 同步更新影响范围、测试说明、风险和 Review 重点。
4. 如果新增了破坏性变更、数据库变更或接口行为变化，必须显式标记。
5. 删除过期内容、错误测试结果和已不适用的风险描述。
6. 确保标题、正文和 Checklist 彼此一致。

## 评审 PR 文档流程

评审时按以下维度给出结论：

| 维度 | 检查点 |
| --- | --- |
| 完整性 | 是否包含背景、变更内容、影响范围、测试、风险、Review 重点 |
| 可理解性 | reviewer 是否能不读全部代码就理解变更目标和范围 |
| 可验证性 | 测试说明是否具体到命令、场景、结果或未测原因 |
| 准确性 | 文档是否与 diff、提交、接口和数据变更一致 |
| 风险披露 | 是否明确兼容性、破坏性变更、性能、安全、数据和部署风险 |
| 可评审性 | 是否指出核心文件、关键逻辑和需要重点判断的问题 |
| 合规性 | 是否无敏感信息、无虚假测试、无未替换占位符 |

评审输出格式：

````markdown
## 评审结论

<通过 / 需要补充 / 不建议提交评审>

## 主要问题

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| <问题> | <为什么影响评审> | <如何改> |

## 缺失信息

- <缺失项>

## 建议补充文本

（可直接复制到 PR 文档中的补充内容）
````

## 质量门禁

以下情况应标记为“需要补充”，不要直接认为 PR 文档合格：

- 只有“做了若干优化”“修复问题”等泛化描述。
- 没有关联背景或无法判断为什么改。
- 涉及接口、表结构、任务、配置，但未说明兼容性和影响。
- 测试说明为空，或写了未实际执行的测试。
- UI 变更没有截图/示例，也未说明不提供的原因。
- 有破坏性变更但未显式标记。
- 没有 Review 重点，reviewer 无法判断优先看哪里。
- 存在未替换占位符、敏感信息、账号、token、密钥或内部凭据。

## 精简模板

适用于纯文档、小修复、低风险变更：

```markdown
## 背景

## 变更内容

## 测试说明

## 影响与风险

## Review 重点

## Checklist

- [ ] 已确认无敏感信息
- [ ] 已说明兼容性和风险
```
